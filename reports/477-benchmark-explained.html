1기존 벤치마크는 어떤 시험인가?

여러 모델에 같은 시험지를 주고 비교하기 위한 규칙 묶음입니다. 영상, 뽑아 볼 프레임, 질문, 답변 형식을 고정합니다. 정답과 비교하는 채점까지 하려면 별도의 정답 자료가 필요합니다.

final_candidates_v1

최종 후보 영상 6개를 확인하고 데모하는 자료입니다.

477_modeling_benchmark_v1

실제 비교 시험의 기준입니다. 공통 64프레임, 프롬프트, 입력·출력 JSON schema와 로더가 들어 있습니다.

고정된 세 가지

  1. 입력: 한 ITEM당 총 64프레임. 프레임은 영상에서 뽑은 이미지입니다. 카메라가 여러 개여도 모두 합쳐 64장입니다.
  2. 질문: 공통 프롬프트. 모델에게 무엇을 판단하고 설명할지 동일한 기준으로 요청합니다.
  3. 답변 형식: JSON schema. 필수 항목, 숫자 범위, 카메라·시각 같은 구조를 정합니다. schema는 답의 형식 규칙이지 정답지가 아닙니다.

공식 입력 경로는 iter_model_frames(item_id)입니다. 정답 caption·answer·bbox·evidence를 이 입력에 추가하지 않습니다.

원래 제안된 모델 비교 구도

P0 CV-only · P1 CV + Clef-Flash · P2 CV + Jev · P3 CV + Clef · P4 Strong VLM

이는 README에 연결된 역할 배정 제안입니다. 모든 모델이 구현·실행되었다는 표시가 아닙니다. Jev나 Clef-Flash의 성능을 이번 실제 결과로 판단할 수 없습니다.

기존 벤치마크는 모델 간 비교를 시작할 기반이었습니다. 추가한 실행기는 실제 CV → Clef → VLM 연결과 단계별 실패를 기록합니다. 그러나 사건 정확도를 채점할 정답·정상 구분은 여전히 부족합니다.

2추가한 파이프라인은 어떻게 움직이나?

같은 입력으로 두 가지 실행을 비교합니다. VLM 단독과 전체 파이프라인을 따로 남겨, 앞 단계 실패를 VLM 책임으로 돌리지 않도록 했습니다.

① 공통 64장

중립 ITEM·카메라 ID와 실제 입력 시각을 준비합니다.

② 로컬 CV

YOLO26s로 객체를 찾고 ByteTrack으로 이어 추적합니다. 기본 실험은 자세 분석도 사용합니다.

③ Clef

CV가 직접 추출한 객체·추적 정보를 받아 다음 처리 방향을 제안합니다.

④ VLM + 검증

deepseek-flash가 같은 64장 이미지를 봅니다. 출력·근거를 확인하고 공통 결과로 변환합니다.

VLM 단독 · vlm_only

64장 → VLM → 출력 검증

CV와 Clef 없이도 답하는지 확인하는 비교 기준입니다.

전체 연결 · cv_llm

64장 → CV → Clef → VLM → 출력 검증

각 단계가 실제 호출·성공했는지와 최종 답이 통과했는지를 별도로 기록합니다.

현재 Clef는 VLM 호출을 줄이지 못하고 있습니다. 검증된 정상 사건 판단이 없어 이번 전체 파이프라인 10건 모두 VLM을 호출했습니다. Clef가 정상 같다고 제안한 것만으로 사건을 숨기지 않습니다.
각 모델이 실제로 받은 입력
  • CV: 원본 공통 64장의 영상 프레임. 추가 프레임이나 crop을 사용하지 않았습니다.
  • Clef: CV가 추출한 정보의 구조화된 텍스트 상태. 이번 실험에서는 Clef에 이미지를 보내지 않았습니다.
  • VLM: 같은 64장을 JPEG 품질 80으로 변환한 이미지와 공통 질문·schema·카메라·시각 라벨. 이번 VLM 요청에는 CV 특징을 추가하지 않았습니다.

같은 64장을 사용해도 모델별 변환과 공급자 내부 처리 방식은 다를 수 있습니다. 따라서 공통 입력만으로 완전한 공정성이 자동 보장되지는 않습니다.

개선은 무엇을 바꿨나?

  • Clef 입력 차단 수정: 토큰 한도를 byte 한도로 잘못 취급하던 조건을 제거했습니다. 요청 크기·시간 제한·$5 예산 보호는 유지했습니다.
  • VLM 시각 표현 개선(v2): 입력 프레임의 실제 시각을 정확히 전달합니다. 답의 시각을 사후에 바꾸거나 허용오차를 늘리지 않았습니다.
  • 별도 JSON 라벨 실험(v3): 문법 오류가 났던 ITEM_04에 JSON 형식 프레임 라벨을 사용했습니다. 한 건 성공이며 전체 평가로 합치지 않습니다.
  • 별도 pose-off 속도 실험: 자세 분석을 빼고 탐지·추적만 실행했습니다. 빨라졌지만 넘어짐 판단 품질이 유지되는지는 미확인입니다. 기본값은 그대로입니다.
  • 평가 방식 개선: 마지막 답만 성공한 경우와 전체 단계가 성공한 경우를 구분합니다. 실패 요청 비용도 무조건 0으로 처리하지 않습니다.

이번 실제 연결은 benchmark CLI 실행 경로입니다. 웹 서비스 ASGI의 실제 Clef/VLM 슬롯 연결까지 완료했다는 뜻은 아닙니다.

3테스트 CSV는 이 순서로 읽으세요

CSV 한 줄은 “한 ITEM을 한 조건으로 한 번 실행한 기록”입니다. ITEM_04를 VLM 단독과 전체 파이프라인으로 실행하면 두 줄입니다. 기존은 각 조건 3회 반복, 새 공통 실험은 1회입니다.

  1. 무엇을 실행했나? item_id, repeat, condition
  2. 마지막 답은 통과했나? status와 validated
  3. 앞 단계까지 모두 성공했나? whole_pipeline_validated, upstream_failure_count
  4. 얼마나 걸리고 무슨 오류가 있었나? latency_ms, errors, upstream_errors
  5. 비용을 얼마나 확인했나? 비용 열과 unknown_billing_requests
CSV 열읽는 뜻주의할 점
attempt_id실행의 이름. 예: ITEM_04-r01-cv_llmr01은 첫 반복입니다. 서로 다른 결과 폴더에서는 같은 이름이 나올 수 있습니다.
conditionvlm_only = VLM 단독 / cv_llm = 전체 파이프라인이 CSV의 cv_llm은 CV→Clef→VLM 연결입니다.
statusok / error / invalid_output 등 실행 결과ok만 보고 전체 성공으로 세면 안 됩니다.
validated최종 출력이 schema·입력 context·근거 참조 검사를 통과했는지True는 사건 정답과 일치한다는 뜻이 아닙니다.
whole_pipeline_validatedCV·Clef·VLM 전체 단계 성공 + 최종 검증 통과VLM 단독의 빈칸은 해당 없음입니다. 기존 CSV에는 이 열이 없습니다.
upstream_failure_count최종 VLM 앞에서 실패한 단계 수1이면 앞 단계 오류가 있었다는 뜻입니다.
latency_ms해당 실행 전체 시간. 1,000ms = 1초71,000이면 약71초. 모델 추론만의 시간은 아닙니다.
estimated_cost_usd해당 실행의 토큰 사용량 기반 비용 추정실제 청구액이 아닙니다. 빈칸은 미확인이고 0과 다릅니다.
known_partial_usage_cost_estimate_usd확인된 요청의 비용만 합친 부분합미확인 요청이 있으면 전체 비용처럼 쓰면 안 됩니다.
unknown_billing_requests비용을 확인하지 못한 요청 수1 이상이면 전체 비용이 확인되지 않았습니다.
actual_invoice_cost_usd실제 청구서 비용현재는 청구 자료가 없어 비어 있습니다.
errors / upstream_errors오류 종류 / 어느 앞 단계에서 실패했는지[]는 해당 목록에 오류가 없음. 다른 열도 함께 봐야 합니다.
stages모델별 호출·성공·시간·비용 등의 상세 기록개선 CSV에 추가된 긴 JSON 열입니다. 깊은 분석은 diagnostics JSON이 편합니다.
CSV에는 사건 정확도 점수가 아직 없습니다. schema·근거 검사 각각의 상세 결과와 모델별 시간은 diagnostics/ JSON을 보면 됩니다. 사람이 사건 판단을 채점한 결과로 오해하지 마세요.

실제 예시 4건을 표시합니다.

대표 함정: status=ok + validated=True + whole_pipeline_validated=False
“앞 단계는 실패했지만 마지막 답은 받았다”는 경우입니다. pose-off의 ITEM_02가 실제 사례입니다. 최종 성공3/3과 전체 성공2/3이 다른 이유입니다.
엑셀에서 열어 보는 가장 쉬운 방법
  1. 아래 파일 목록의 evaluation.csv를 열거나, 엑셀에서 데이터 → 텍스트/CSV에서 가져옵니다.
  2. UTF-8 인코딩, 쉼표 구분을 선택합니다. JSON 열 안에도 쉼표가 있으므로 줄을 손으로 쉼표마다 나누지 마세요.
  3. 먼저 condition으로 조건을 나누고 validated=False를 확인합니다.
  4. 전체 파이프라인은 whole_pipeline_validated=False도 별도로 확인합니다.
  5. 시간을 초로 보고 싶으면 latency_ms 값을1,000으로 나눈 열을 만듭니다.

기존 CSV는 전체 단계 검증 열이 없으므로 upstream_errors와 diagnostics도 봐야 합니다. 비교 분석에서 재계산한 기존 전체 성공은9/21입니다.

같은3항목의 CV 시간 중앙값은 34.5% 감소했습니다. 탐지·추적 관측값은 같았지만 자세 단서는 없어졌습니다. 전체 단계가 양쪽 모두 성공한2항목만 비교하면 전체 시간 중앙값은 68.71 → 53.33초,22.4% 감소했습니다.

중앙값은 시간을 순서대로 놓았을 때 가운데 값입니다. 평균과 다릅니다. CV·Clef·VLM 시간의 중앙값을 더해 전체 중앙값으로 쓰면 안 됩니다.

넘어짐 정확도를 확인하기 전에는 자세 분석을 기본으로 끄지 않습니다. 속도만 좋아졌다는 결과로 행동 판단 품질이 유지됐다고 말할 수 없습니다.

주요 병목은 CPU의 탐지·자세 분석

개선 공통 전체 파이프라인의 단계 시간 중앙값은 CV48.36초 / Clef5.22초 / VLM12.68초였습니다. 한 실제 항목의 CV 내부 측정은 객체 탐지19.31초, 자세17.35초, 라이브러리 import5.02초, 추적0.25초였습니다.

따라서 다음 속도 후보는 자세 분석을 필요한 때만 하기, 모델을 유지하는 worker, GPU 실행입니다. 이 후보들은 아직 실제 품질·지연 비교까지 완료한 개선이 아닙니다.

64장 균등 추출에 대한 판단

VLM 공통 비교와 첫 실행 점검에는 합리적인 시작점입니다. 모두 같은 총 이미지 수로 질문에 답하고, 정답을 보고 사건 장면을 골라 주는 편향을 막을 수 있습니다. 전체 시간을 넓게 훑는 데도 도움이 됩니다.

하지만 YOLO·ByteTrack·행동 규칙 모두에 최적인 입력은 아닙니다. 탐지에는 각 이미지의 대표성과 정답이, 추적에는 관측 연속성이, 행동에는 사건 전후 정보가 필요합니다. 단일64장이라는 숫자로 이 요구를 모두 충족할 수는 없습니다.

  • 추적 비교: 같은 사람의 ID 정답을 가지고 연결·끊김을 평가해야 합니다. ByteTrack은 객체 연결 모델이지 사건 정답을 제공하는 모델이 아닙니다. ByteTrack 원논문.
  • 행동·위험 비교: 사건 시작·끝·정상 여부와 구역·시간 정책이 필요합니다. 사람 박스 하나나 높은 탐지 confidence로 넘어짐·침입을 확정하지 않습니다.
