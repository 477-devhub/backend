# Clef가 현재 효과를 내지 못하는 이유

2026-10-08 저장된 실제 응답과 현재 코드 분석. 추가 모델/API 호출은 없으며,
CV+VLM을 새로 실행하거나 사건 정답과 비교한 결과가 아니다.

## 팀원의 의견은 어느 범위에서 맞는가?

**현재 구조에서는 Clef를 빼는 것이 지연·호출 비용·실패 지점을 줄일 것으로
판단한다. 하지만 사건 정확도까지 더 좋다는 것은 아직 입증하지 못했다.**

가장 결정적인 이유는 **Clef가 만든 정보가 실제 처리 선택이나 최종 VLM 판단에
영향을 주는 경로가 현재 없기 때문**이다. 공급자 응답이 실패해서만 생긴 문제가 아니다.
Clef가 성공한 공통7항목에서도 효과가 제한되어 있었다.

현재 측정은 VLM 단독과 CV→Clef→VLM이다. **CV→VLM만 실행한 대응 비교는 없다.**
사건별 정답·정상 영상 구분도 없어 어느 구성이 사건을 더 정확히 맞히는지 채점할 수 없다.

| 확인한 사실 | 실제 근거 | 해석 |
|---|---|---|
| VLM 호출 생략0건 | 추가 전체 파이프라인10건 모두 VLM 호출 | Clef를 넣어도 VLM 비용·시간을 줄이지 못함 |
| Clef의 시각 입력0장 | adapter metadata `images_sent=0` | 이번 Clef는 영상 대신 CV의 구조화된 관측만 평가 |
| VLM은 CV/Clef 결과를 받지 않음 | 실행기는 원래 request를 VLM에 전달. adapter는 features_json 입력을 거부 | 현재 CV/Clef가 사건 설명을 보강하는 구조가 아님 |
| 단독·전체의 VLM 입력 구성 일치7/7 | 이미지 JPEG hash, prompt/schema/프레임 라벨/시각 지시 hash, 출력 상한 등 비교 | 전체 출력이 다르더라도 Clef가 새로운 판단 정보를 제공한 결과로 볼 수 없음 |
| Clef 성공7건 중 human_review6, invoke_vlm1, no_action0 | 실제 Clef decision | Clef 자체도 대부분 불충분한 입력이라고 판단 |
| Clef route confidence0.229~0.3946 | 공통7건 실제 응답 | 라우팅 확신이 낮음. 사건 정답 확률이나 event confidence와 동일하지 않음 |

## 결정적 원인 1: 처리 선택이 항상 같은 결과로 끝난다

`app/eval/benchmark_baseline.py:171`의 `_safe_route()`는 현재
`invoke_vlm=True`, `normal_assessment_available=False`를 반환한다.
Clef가 제안한 방향은 저장하지만 실제 VLM 호출 여부는 달라지지 않는다.

이것은 검증된 정상 assessment가 없는 상황에서 사건을 누락시키지 않으려는
보수적인 처리다. **Clef를 실패시키는 입력 문제를 해결하지 않은 채 이 보호 조건만
끄는 것은 해결책이 아니다.** 단순히 uncertain=False나 위험축0을 넣어 생략을
허용하면 실제로 모르는 사건을 정상으로 처리할 수 있다.

현재 효과는 “다음 단계가 어차피 실행되는 중간 확인 단계”에 가깝다.
속도·비용을 줄이려던 라우터 역할은 작동하지 않는다.

## 결정적 원인 2: Clef에게 사건을 확정할 재료가 부족하다

공통7항목의 CV 상태는 모두 다음과 같다.

- `zone_configured=false`: 제한 구역이 정의되지 않았다.
- `event_classifier_available=false`: 탐지·추적과 별개인 검증된 사건 판단기가 없다.
- 위험축이 미측정(null): 명시적인 정상·저위험 판단을 만들 수 없다.
- 배회는 화면에 머문 후보이며 실제 배회 확정이 아니다. 침입도 구역·허용 정책 없이 확정할 수 없다.

Clef adapter의 질문 자체도 “구역·위험축·사건 판단기가 없으면 추가 검토”를
요구한다(`clef_benchmark.py:138~151`). 실제7건 모두 `cv_uncertain=true`,
`reason=cv_information_incomplete`였다. CV가 같은 부족 상태를 계속 보내면
Clef의 모델이나 임계값만 바꿔도 해결되기 어렵다.

예를 들어 사람 좌표가 담을 넘어 바뀌어도, 그곳이 출입 금지인지·허용된 행동인지
모르면 침입을 확정할 수 없다. 오래 보인 사람도 대기·업무·배회 중 무엇인지
정책과 장면 맥락이 필요하다. 현재 Clef에게는 원본 이미지도 보내지 않는다.

## 결정적 원인 3: CV와 Clef의 정보가 최종 답에 합쳐지지 않는다

현재 연결을 정보 흐름으로 보면 다음과 같다.

```
64프레임 → CV 관측 → Clef 제안 → 기록
64프레임 ───────────────────→ VLM 판단 → 최종 답
                         실제 VLM 호출은 항상 실행
```

`benchmark_baseline.py:587`에서 CV 관측을 Clef에 전달하지만, VLM 호출은
`:599`에서 원래 request를 사용한다. `deepseek_benchmark.py:110`은
features_json이 있으면 입력 오류로 처리한다. 이는 공통 비교에서 VLM의 입력을
동일하게 유지하려고 구현한 것이다.

따라서 **Clef만 빼고 CV를 그대로 앞에 두면, CV도 최종 VLM의 사건 정확도를
직접 높이는 역할은 아직 하지 않는다.** CV의 기능은 관측·추적 자료 생성이며,
그 자료를 어디에 사용할지 명확히 해야 한다.

## 함께 확인해야 할 입력·추적 문제

64장은 모든 카메라를 합친 입력 예산이다. 실제 ITEM_04는 카메라당21~22장,
관측 간격 중앙값 약1.67~1.73초다. ITEM_07은 카메라당32장,약1.0~1.03초다.
ByteTrack은 그 사이의 모든 원본 프레임을 보는 것이 아니라 선택된 이미지들을
이어서 처리한다. 짧은 행동이나 추적 연결에 불리할 수 있다.

실제 관측에는 ITEM_03 미추적 탐지365/1,102, ITEM_05 103/206이 있었다.
ITEM_02는64장 중38장에서 사람 탐지가 없었다. **이 수치를 정답 기반 추적 실패율이나
사람 누락률이라고 부르면 안 된다.** 실제 사람이 있었는지와 같은 사람인지 확인할
정답이 없어, 조사할 후보 증상으로만 사용할 수 있다.

구역 미설정·불완전 사건 의미·희소한 추적은 Clef에 전달되기 전부터 존재한다.
Clef가 이미 빠진 시각·운영 정보를 숫자만 보고 복원해줄 것으로 기대하기 어렵다.

## 원래 실패들과 이번 구조적 문제를 구분하기

| 현상 | 원인 판단 | 현재 상태 |
|---|---|---|
| 과거 Clef6건 호출 전 차단 | byte/token 상한을 혼동한 변환 코드 | 수정. 기존 차단 ITEM_03/06 실제HTTP200 확인 |
| pose-off ITEM_02 ClefHTTP429 | 공급자 응답이 무료 일일 할당량 소진을 명시 | 계정 문제. 모델 판단 능력이나 VLM 오류가 아님 |
| VLM 근거 시각 불일치 | 입력 라벨의 시각 표현이 실패에 기여했을 가능성 | v2 개선 후 새 공통 실험의 잘못된 입력 근거 참조0건. 내부 원인 전부 입증한 것은 아님 |
| 공통 v2 ITEM_04 단독 JSON 오류 | 원본 답의 `timestamp_sec=` 등 문법 오류 | 실패 보존. 별도 v3단건 성공만 확인 |

| Clef 성공해도 지연·호출 수가 안 줄어듦 | 처리 선택 고정 + 최종 입력에 정보 미반영 | 현재 효과 부재의 가장 직접적인 구조적 원인 |

VLM 단독6/7과 전체7/7의 차이를 Clef의 정확도 향상으로 설명해서도 안 된다.
VLM 입력 구성은 동일했다. 답변 변동의 구체적 원인은 확인되지 않았으며,
표본1회·정답 부재·출력 문법 차이를 고려해야 한다.

## Clef를 빼면 얼마나 나아질까?

실제 공통7건의 Clef 단계 시간 중앙값은 **5.22초**다. 같은7건에서 Clef에
사용한 토큰 요금 추정 합계는 **$0.03765024**이며 실제 청구액은 아니다.

각 실행의 전체 시간에서 해당 실행의 Clef 시간만 빼보면 중앙값은
71.34→64.97초다. **이 값은 저장된 시간으로 계산한 가상 제거 추정이다. 실제
CV+VLM 실행 측정값이 아니며 재실행 시 API·변환·스케줄링 시간이 달라질 수 있다.**

더 큰 지연은 CV 중앙값48.36초다. Clef 제거만으로 그 병목까지 해결되지는 않는다.
별도 pose-off에서 CV 시간이 줄어든 것은 이미 확인했지만 행동 품질 유지 검증은
남아 있다. 정확도·지연·비용·실패율을 각각 비교해야 한다.

## 실패 해결의 우선순위

### 1. 먼저 사건 채점을 가능하게 한다

중립ITEM과 실제 정답의 매핑, 정상 영상, 사건 시작·끝, 근거 채점 기준을 확보한다.
공통 사건6종과 원본 사건명 매핑도 확정한다. 정답은 평가에서만 사용한다.
모든 구성을 같은 사건·근거·누락 기준으로 채점해야 성능 향상을 말할 수 있다.

### 2. CV가 실제 어떤 역할을 할지 확정한다

침입·배회에는 카메라별 구역 polygon·허용 정책·시간 기준이 필요하다.
넘어짐에는 시간에 따른 자세 변화와 추적 연속성을 확인해야 한다. 탐지 신뢰도를
사건 신뢰도로 바꾸지 않는다. 현재의 부족한 자료를 정상으로 포장하지 않는다.

공통64프레임 비교는 그대로 둔다. 더 촘촘한 추적·crop·추가 관측은 별도 실험으로
분리하고 frame budget·전처리 비용을 기록한다.

### 3. Clef 없는 대응 비교를 실제 실행한다

같은7ITEM·같은64장·같은prompt/schema·같은VLM 변환으로 다음을 비교한다.

1. VLM 단독.
2. CV→VLM, CV 특징을 VLM에 추가하지 않는 조건: Clef 호출 제거 효과만 분리.
3. CV→Clef→VLM, 기존 조건: 같은 입력과 사건 정답으로 비교.

CV의 시간 정보를 VLM 판단에 활용하려면 **CV 특징을 추가하는 별도 실험**을
정의한다. 기존 공통 조건과 혼합하지 않는다. 같은 반복 수·cold/warm 구분·실행
순서 조건을 기록한다. 현재$5 누적 예약이 거의 소진되어 이 추가 유료 비교는
실행하지 않았다. 기존 ledger를 초기화하지 않는다.

### 4. Clef의 역할을 검증 가능한 것으로 좁힌다

당장은 주 실행 경로에서 제외하고 **비동기 참고 평가**로 남기는 방향을 우선
검토한다. 이 경우 최종 답을 기다리게 하지 않으며 Clef 결과를 정답과 대조해
정상·검토·VLM 추가 분석 구분이 실제로 유용한지 확인한다.

Clef를 다시 처리 선택에 쓰려면 최소한 아래 성과가 확인되어야 한다.

- 사람 검토 없이 넘어간 사건의 누락까지 포함한 정답 기반 평가.
- VLM 호출 감소가 실제로 있고 전체 시간·총비용도 감소.
- 정상 판단의 신뢰도와 근거가 검증되며 기존 자동 억제 계약을 충족.
- 실패·불확실 입력은 사람 검토로 복귀하고 모든 입력을 평가 분모에 유지.

근거가 없으면 Clef를 계속 주 경로에 넣을 필요는 없다. 현재 문제를 해결하기
위해 Clef를 반드시 유지해야 하는 상황도 아니다.

## 권고

**현재 데모의 주 경로는 Clef 없이 단순하게 만드는 방향이 타당하다.** 다만 먼저
CV가 VLM 판단에 기여하는 경로를 만들지, 독립 관측용으로 둘지 정해야 한다.
이번 분석의 우선 해결 대상은 Clef 모델 교체보다 **사용되지 않는 중간 단계,
불완전한 사건 입력, 정답 채점 부재**다.

이 문서는 분석과 구현 우선순위다. 라우팅 조건·모델 입력·실행 코드는 변경하지
않았으며 새로운 유료 비교, 모델 정확도 검증, 새 테스트 통과를 주장하지 않는다.
